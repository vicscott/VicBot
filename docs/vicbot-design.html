Design proposal · v0.9 · living document

Route the task,
not the agent.

Every product I read binds a harness to an agent, a bot, or a session. VicBot binds it to a task — and lets the task change harness mid-work. That one difference decides everything else.

What changed

v0.9: context, from AutoSwarm.

  • §18 Context: the transcript stays with the harness and is never copied; a continuing run gets a delta, not the bundle; rework gets a fixed five-field block; VicBot's own fixed block has a 1,500-character ceiling; peer messages are enveloped and carry the rule “every reply wakes its recipient”.
  • Compaction runs only when the harness cannot compact itself (§18 Context); a resumed session's delta always carries the policy (§15 Session).
  • Two refusals added to §22 What we don't build, one risk, five decisions.

v0.8: server and clients, and what LoopForge does better.

  • New §19 Deployment: VicBot ships as a server and clients. No public port; a private network; paired, scoped devices instead of accounts; a versioned /v1 gateway; offline queueing and first-answer-wins; a web app and the CLI first, then push, a chat bridge and execution nodes. Rule 9.
  • §07 The loop: a run ends by writing a verdict file: pass, rework, fail, human, overflow or handoff.
  • §12 Verification: a pass needs a changed output; checks never fail on style; you may accept the current result.
  • §09 Handoff: the brief is validated, and the receiver gets a code-built extract instead of the history.
  • §05 The contract: effort is judged by impact; an overflow verdict escalates (§10 Orchestration).
  • §24 Migration grows to 21 steps; three new risks; three new open questions.

v0.7: bounds. §13 Bounds collects every ceiling and adds one budget per root task and a quick path with no extra model call. Contract tiers, one rework per check, templates for the host, and cheaper discussions.

Part I

The idea

01

The thesis

In shortVicBot sends each task to the cheapest shape that could work and upgrades it when there is evidence the shape is not enough. Nine rules constrain every later decision.

VicBot is a router with a memory. You give it a job; it decides how much structure the job needs, runs it on the cheapest shape that could work, and — when the cheap shape proves insufficient — promotes it, carrying the evidence with it.

Nine rules constrain the whole design. Everything below is a consequence of one of them.

#RuleWhat it forbids
1 A task outlives its harness. any state that lives only inside a run
2 No feature requires a particular harness. A harness that can do nothing must still produce a working product. capability as a precondition; this is the disentanglement test
3 Under-route, escalate on evidence. predicting complexity up front; escalating on a count or a clock
4 The thing that deliberates does not get to permit. the router, the chair, or a discussion granting authority
5 The worker never verifies its own work. a participant concluding, or a chair signing off on its own synthesis
6 A pause is a state, not a dead process. an approval, a question or a lost session forcing a restart
7 A task is woken, not started. A person's message is one of several kinds of event. assuming somebody is watching; streaming as the only way to deliver
8 Every cycle has a ceiling, and every ceiling is a number. Steps, retries, rounds, hops and wakes all stop at a limit set in config. a limit that is a model's judgement, such as “stop when it seems done”
9 The server is the product; a client is a window. Everything a task needs lives on the server. A client holds nothing that would be lost if it closed. state, credentials or decisions that exist only in a client

Non-goals, stated up front. VicBot is not a teammate with a personality, not a workspace, not a container platform, not multi-tenant. It is one person, one server, any number of clients, and any number of harnesses. Every design choice below is cheaper because of that.

02

Why not copy any of them

In shortEvery reference product ties a harness to a bot, an agent, a session or a workflow role. VicBot ties it to a task, so it borrows only the parts that survive a change of harness.

The references agree on almost everything except one thing, and that one thing is the thing VicBot is for.

03

Three layers, three lifetimes

In shortWork is split into a Task (what you asked for), a Run (one attempt on one harness) and a Session (the harness's own context), so every question has exactly one home.

The central mistake available to VicBot is to let one row mean everything. Today a Task holds the route, the harness, the session id, the budget, the tokens, the result and the handoff parent. That works at 1,700 lines and breaks the first time a task needs a second run.

Task
What the person asked for. Durable, person-facing, routable, handoff-able. Survives every run and every harness. May carry a contract, and may have children.
id · goal · contract? · shape · status · rootId · parentId · depth · cost
Run
One attempt at advancing the task, on one harness, in one session. Created by a route, a handoff, a retry, a verify, or a resume. A run is durable and may span several jobs — a job is one lease on the worker, and it ends whenever the run parks (§14 Waking).
id · taskId · harness · sessionId · effort · status · budget · pending
Session
The harness's own context. Owned by the harness, disposable by design, resumable by contract.
id · harness · cwd · resumeCursor · state · lostReason

The payoff is that every question now has exactly one home. “What did this cost?” is a Task question. “Which harness is running?” is a Run question. “Can we resume?” is a Session question.

Nothing later in this document is a fourth layer. The chair (§10 Orchestration) is a run of the task. Every cast member is a run of a child task. A discussion round is a set of runs. If a proposed feature needs a new table, it needs a paragraph in “What we don't build” first.

04

Topology

In shortYou only ever talk to the host, from any client. Execution bots send reports up to the host, which renders most of them from templates and calls a model only to interpret or compress.

Three layers described what a piece of work is — task, run, session. This is a different axis: who talks to whom. The two get confused the moment somebody says “layer”, so they are kept apart on purpose. Data layers are covered in (§03 Three layers); actor layers are here.

Three actor layers

Only the host has an edge to the person

An execution bot's message is a report, not a reply. It has no channel to the person — not to stream, not to ask, not to notify. Everything it wants said goes to the host, which decides what the person actually sees.

That single rule is what makes the rest work. It is why the person never has to know which harness ran, why there is one notification stream instead of six, and why a discussion can be as noisy as it likes without becoming noise.

The topology does not change when VicBot moves to a server (§19 Deployment). The person reaches the host through clients: a web page, a terminal, a chat app, a phone notification. Each client is a view of the same mailbox, so a question asked on the laptop can be answered from the phone, and nobody has to know which client was used.

The host is a mailbox

“Message box shared by the person and all routes” is the right picture, and it is literally the inbox and outbox from Waking with an owner: 

interface HostMailbox {
  inbound:  UserMessage[];   // the person → the host
  upward:   Report[];        // execution bots → the host; never delivered raw
  outbound: Outgoing[];      // the host → the person; the only writer
}

interface Report {
  from: string;              // a run, the chair, the keeper, the verifier
  taskId: string;
  kind: "progress" | "result" | "blocked"
      | "question" | "approval" | "contradiction";
  body: string;
  evidence: string[];        // pointers the host must carry through, never drop
}

An approval is a report with a question attached: the host renders the card, the person answers, and the answer is an inbox event that resumes the parked run (§14 Waking). The running bot never sees the person and never sees the answer as prose — it sees the decision as a tool result.

What the host decides, and what it only reads

The host decidesThe host only reads

whether to interrupt the personwhether the loop guard fired
how to summarise a reportwhether a check passed

The right-hand column is the whole reason the host is not the task's owner. The host narrates state; it does not set it. Status, budget, escalation triggers and check results are computed by the loop's gate (§07 The loop) and stored on the task row (§03 Three layers). A host that could set them would be a second source of truth, and “the host decided to pause” is not a reproducible reason for anything.

The host compresses, it never truncates

A single conversational surface is also a single point of information loss. If the host summarises a chair's synthesis into two sentences and drops the rest, the person cannot tell whether the summary was faithful.

Every summary carries a pointer. The host may compress a report to one line, but the line is attached to the full report in the ledger, and the full report is one click away. Compression is a service; truncation is a bug.

Why one voice is worth it

OpenMausBot makes every bot a contact in the sidebar — a deliberate product choice, and the right one for a chat app where the bots are characters. It is the wrong choice for a router, because the person asked VicBot, not “the omp bot”. One voice means the routing is invisible when it works, which is the point of routing.

The host is mostly not a model

A host that calls a model for every report adds a model call to every task and puts a model between you and every fact. So the host is a template renderer first and a model second. It calls a model only where a template cannot do the job:

Host jobHowModel call

The target is no host model call on the quick path (§13 Bounds). The ledger counts host calls per task, so a rising count shows up as a number, not a feeling.

The cost is that the host is a bottleneck and a single point of failure. It is stateless per turn — it reads the task row and the mailbox, and holds nothing between turns — so it can be restarted freely, and its own loop guard applies to it like any other run (§07 The loop).

Part II

Doing one task

05

The contract

In shortA task's definition of done is a contract. Effort is judged by impact. Most tasks use an implicit contract; checks make a task checkable, not orchestrated.

Today a task is a string. That is enough for “rename this variable” and useless for “ship the feature”. The question “how do you define a complex task” has a clean answer, and it is not “write a longer prompt”.

Complexity is the presence of a contract, not the length of the prompt. A one-line task with acceptance checks is complex. A paragraph with none is simple. This makes “is this complex?” a checkable predicate instead of a judgement call.

interface Task {
  goal: string;              // one sentence, what the person wants
  contract?: Contract;       // present ⇒ complex
}

interface Contract {
  acceptance: Check[];       // how we know it is done — the whole point
  constraints: string[];     // what must not happen
  artifacts: string[];       // what must exist at the end
  budget: { minutes: number; cost: number; hops: number };
}

type Check =
  | { kind: "cmd";   run: string; expect: "exit0" | { stdout: string } }
  | { kind: "file";  path: string }
  | { kind: "test";  run: string }
  | { kind: "judge"; question: string; threshold: number }
  | { kind: "human"; ask: string };

Where a contract comes from

The personwrites it, or picks a template — fix-a-bug, ship-a-feature, investigatealways allowed

Contract tiers

Proposing a contract is itself a model call plus a confirmation from you. Doing that for every task is the over-analysis the router exists to avoid, so most tasks never see a proposal:

TierWhenCost
implicitquick and standard tasks, by defaultnothing: done means a pass verdict, every file the task names exists, and at least one of them changed since the run started (§12 Verification)
proposeddeep tasks, unattended tasks, and any task with a gated, irreversible actionone cheap planning call and one accept/edit from you
writtenyou wrote one, or picked a templatenothing extra

The number of checks does not choose the shape. Rule 3 forbids predicting complexity, and a contract with five checks is often still one run's work. A contract makes a task checkable. Only genuinely parallel work (independent artifacts with no order between them) or your say-so starts a task orchestrated. Everything else starts single and escalates on evidence (§10 Orchestration).

Decomposition is child tasks, not a new concept

A complex task becomes a tree. There is no steps table, because a step needs a run, a session, a budget, a status and a result — and that is a task. Adding steps would duplicate Task and then drift from it.

The rule that keeps this from becoming a loophole: a child's contract is a subset of its parent's — same as trust. A child cannot invent an acceptance check the parent did not ask for, and cannot drop one the parent did.

Size is judged by impact, not by length

Effort is decided by what a task touches, not how long the request is. The rules use the request's paths and verbs; when they cannot tell, the default is the smaller size.

EffortImpact
quickone area, at most 3 files, no change to an interface, a data model or a schedule
standardseveral areas, or about 4 to 10 files
deepmore than that, or any change to an interface, data, a migration, or anything irreversible

A run that finds its task is bigger than its effort files an overflow verdict (§07 The loop) instead of pushing on. That is the honest version of under-routing: start small, and let the work say it is not small. The sizes follow LoopForge's small, medium and large routes.

06

Catalog and router

In shortThe router reads a catalog of installed harnesses and only picks a shape. When it is unsure it picks single, because a single task can always escalate.

A router that routes to a missing binary is worse than no router. So the catalog comes first, and the router reads it. With third-party harnesses the catalog stops being a source file and becomes a scan of installed manifests. 

// discovered at startup: ~/.vicbot/harnesses/*/harness.json
{
  id: "omp",
  protocol: "1.2",
  probe: ["--version"],
  capabilities: { approvals: true, steering: false, resume: "cursor", … },
  routes: ["build"],
  cost: "subscription"
}

The router picks a shape, and it is allowed to be wrong

Because a wrong single escalates (§10 Orchestration), the router's job is not “predict how complex this is”. It is “pick the cheapest shape that could work.” That is a much easier question, and getting it wrong costs one run instead of a whole orchestration.

  1. Rules. Deterministic, free, explainable: a path in the input, a verb, a file extension, an explicit “use X”. Most tasks stop here.
  2. A small model. Only when the rules are ambiguous, and only among harnesses that are installed, probed and allowed to serve that route. It returns a shape and a confidence — nothing else. No tool access, no policy access.
  3. Under-route. Below the threshold, pick single rather than asking or guessing orchestrated. The escalation ladder makes that the safe answer, and it is the one thing a router can always afford.

The router's output type is Shape. Not a harness, not a policy, not a trust level. If it could return a policy it would be a permission system, and permission systems do not get to be probabilistic.

The designated route

When the person names a bot or a harness, the router is skipped — but not the policy. A designated route still resolves a trust level, still probes the harness, and still fails at intake (not at run time) if the named harness is not installed. Pre-designation is information about intent, not a grant of authority. A designated task also does not escalate on its own: a second failed check moves it to blocked with an offer to escalate, because you chose the harness and changing it is your call.

07

The loop

In shortOne loop drives one run: claim, build context, think, gate, act, settle. A run ends by filing a verdict file, and the gate after each step is the only place a run can stop.

One loop, in one file, owning one run. The harness is a generator that yields events and can be spoken to while it runs — that is the difference between reading a CLI and supervising one. 

// harness/index.ts — the contract every harness implements, first-party or not
interface Harness {
  manifest: Manifest;                // id, protocol, capabilities, routes, cost
  spawn(spec: RunSpec, io: HarnessIO): HarnessRun;
}

interface HarnessRun {
  events: AsyncIterable<VEvent>;
  answer?(id: string, d: Decision): void;   // approve / deny, mid-run
  steer?(text: string): void;              // a message into the live turn
  sessionId(): string | null;
  kill(): void;
}

Today Harness is { id, bin, argv, parse } — a pure function from a JSON line to events. That is enough to read a harness and not enough to answer one. Moving the process inside the adapter is what makes answer and steer possible, and it is the single highest-value change in this document.

A run is entered by a job (§14 Waking): one lease on the worker, claimed by compare-and-set. When the run parks, the job ends and the run stays a row. Everything below happens inside one job.

  1. claim. Compare-and-set queued → running, and take the inbox's pending events for this task. Two workers, one winner.
  2. context. Build the turn: system, history, the contract, and the tool list from the gateway. The same builder for every harness.
  3. think. harness.spawn(). Consume events. Text and thinking stream to the UI as they arrive.
  4. gate. After every step: budget, loop guard, cancel, and any pending approval. This is the only place a run can stop — and the only place the host's “continue” and “pause” come from (§07 The loop).
  5. act. Tool calls execute through the gateway, or — for a CLI that owns its own tools — come back already executed and are recorded, not re-run.
  6. settle. Persist the transcript and the ledger row, then decide: continue, park, or end. The decision is a value, not a control-flow accident.

↻ 6 → 2 until the decision is “park” or “end”.

“End” has three shapes and they are not the same thing: send (a row in the outbox), silence (nothing to say, recorded as a decision), or defer (a request for a person, and the run parks). A run that ends without one of those is a bug, not a quiet success.

The run files a verdict

How a run ends is a verdict, not a guess from its final text. The run writes one JSON file, .vicbot/verdict.json in its working root, and the gate reads it. Any harness that can write a file can file one, so this needs no capability (§20 The harness boundary). 

interface Verdict {
  decision: "pass" | "rework" | "fail" | "human" | "overflow" | "handoff";
  reason: string;            // required: the facts behind the decision
  ask?: string;              // required for human: exactly what the person must decide
  brief?: Brief;             // required for handoff and overflow (Handoff)
  findings?: { title: string; severity: string; evidence: string }[];   // at most 50
}
DecisionThe gate does
passruns the checks (§12 Verification)
reworksends the work back once, with the reason as the new brief
failends the run as failed; it is never retried
humanparks the run on waiting_input with ask as the card
overflowthe task is bigger than its shape: escalates once (§10 Orchestration)
handoffvalidates the brief and proposes a handoff (§09 Handoff)

Every field is length-capped and a reason is required. A run that exits without a verdict gets one short follow-up turn: “do not redo the work; file the verdict”. A second miss is read as fail. A harness that cannot write files falls back to parsing a tag in its final answer, and the ledger records that fallback with its reason. The verdict is borrowed from LoopForge's submit_gate_result.

The loop guard asks before it kills. Structural fingerprints first — the same call three times, the same error three times, four failing steps, five steps that only repeat earlier calls — then a cheap judge, then a note, then a cap. Killing on the first repeated call fails legitimate polling; never killing fails the wallet.

08

Policy, not argv

In shortSandbox and approval settings move out of the CLI flag builders into one policy table. A handoff may lower trust, never raise it.

Today the sandbox and approval posture live inside the argv builders: --approval-mode=yolo, --permission-mode workspace-write, sandbox_mode="workspace-write". That is a policy decision hiding in a string concatenation, and it is exactly the coupling every reference avoids. 

// engine/policy.ts — one table, read by every adapter
type Trust = "read" | "workspace" | "full";

interface HarnessPolicy {
  trust: Trust;
  approvals: "never" | "on-request" | "always";
  writableRoots: string[];      // resolved before spawn, never by the model
  network: "off" | "allowlist" | "all";
  maxMinutes: number;
  maxToolCalls: number;
}

function resolve(route: Route, effort: Effort, trust: Trust): HarnessPolicy { … }

The rule that makes this safe: a handoff may lower trust, never raise it. A read run that decides it needs to write must hand off to a new run, and that run starts at the trust the person granted the task — not at the trust the previous run wanted. The same rule applies to a child task (§05 The contract) and to a cast member (§11 Discussion).

09

Handoff

In shortThe model asks for a handoff with a typed brief that is validated before sending. The receiver gets a code-built extract, not the history. VicBot decides route, depth and trust.

A handoff is the only place where one harness's opinion becomes another harness's instruction, so it is the place to be least clever. It is also the simple case of orchestration: one task handing to one other task.

The model proposes, VicBot decides

Decided byWhatWhy
the modelthat a handoff is needed, and the briefit is the only one who knows what it could not finish
VicBotwhich route and harnessthe model would pick the one it likes, not the one that fits
VicBotthe depth and the roota model that can reset its own depth can loop forever
VicBotwhere the result landsotherwise a run can write into a task it was never part of
VicBotthe trust the new run starts withlowering is safe; raising needs a person

The brief is typed, not prose

interface Brief {
  goal: string;              // one sentence, the outcome
  done_when: string;         // how the receiver knows it is finished
  constraints: string[];     // from the person, quoted — not paraphrased
  artifacts: string[];       // paths, ids, urls the receiver must read itself
  tried: string[];           // what the sender already did, so it is not redone
  open_questions: string[];  // what the sender could not resolve
}

OpenBot's finding is the one to keep: free text is how a handoff goes quietly wrong. The receiver infers the intent, guesses the constraints, and when it guesses wrong it does not fail — it answers something else confidently. A typed brief makes the guess visible.

The brief is validated, and the receiver gets an extract

Talking directly costs too much, and a free-form document is not read carefully. The brief sits between the two, and two rules make it work:

  • It is validated before it is sent. goal and done_when must be non-empty, every path in artifacts must exist, no field may contain an unfilled placeholder, and the whole brief fits its cap. A brief that fails is returned to the sender once, with the errors. Wording and layout are never checked.
  • The receiver gets an extract, not the history. VicBot builds the receiver's prompt from the brief's fields by code, adding the parts of the contract the receiving route owns. The receiver reads source files only when the extract is missing something or contradicts itself.

Both rules come from LoopForge's stage templates, where a validator blocks missing sections and empty content, and each stage receives only the sections its role needs.

A failed hop is said out loud. When a handoff exhausts its retries, the originating task gets a message saying nothing came back. Otherwise a question handed on and never answered is indistinguishable from a slow one, and the conversation just stops.

Orchestration

In shortIntake picks single, orchestrated or designated. A single task escalates once on evidence: a check failing twice, or an overflow verdict. Running out of budget asks you instead.

This shape came from the person building VicBot, and it is better than what I had. Three routes at intake, and — the good idea — a cheap route that can escalate. My version routed once, up front, and never reconsidered.

Three shapes at intake

The router picks a shape. It still never picks a permission, a trust level, or a policy — those come from the policy table (§08 Policy, not argv) and, where it matters, from the person.

Who owns what

The host bot, and the line it does not cross

The host is a bot. It routes, it monitors, it talks to the person, and it owns the mailbox (§04 Topology) — all of that is judgement, and judgement is what a model is for. What it does not do is own the task's state, and that line is worth drawing explicitly because crossing it costs four things:

  • Two sources of truth. If the host can set a status, then “the host said pause” and “the budget ran out” are both reasons, and someone has to arbitrate between them.
  • An unreproducible pause. Pause and resume only hold their guarantee if the gate is deterministic. A model's pause cannot be replayed, tested, or explained after the fact.
  • A second handoff that can fail. Host → chair is a message between two models. It can be lost, misread, or answered twice.
  • An unauditable record. The ledger says what happened. If the host can change what happened, the ledger is a story the host tells.

So the split is: the host narrates state; the loop's gate sets it. The host reads the task row and says “I paused this because the budget ran out at 14 minutes” — a sentence generated from a fact, not a decision that created one.

One model call the host does make. It may ask a model exactly one question before work starts: is this one task or three? That is a decomposition judgement, its answer is a child list the person can see, and it is the only place the host writes structure rather than reading it.

Escalation, and the consequence nobody expects

Escalation is triggered by evidence, never by a count or a clock:

TriggerWhy this and not “after N runs”
an acceptance check failed twice: once reworked, still failing (§12 Verification)the only signal that says the work is not done
the loop guard said “stuck twice”a count of runs says nothing about progress
not a trigger: the budget ran out before doneescalating would spend money nobody approved; the task moves to blocked and asks you (§13 Bounds)
the verifier disagreed with the workera disagreement is information; a retry is not
the person says “this needs more than one”the cheapest trigger, and it must always work
the run filed an overflow verdictthe worker found the task is bigger than its shape, and said so with a brief

And the escalation carries the evidence — the failed check, the stuck fingerprints, what was tried. A re-route without new information is a coin flip with a delay.

The consequence: you can afford to under-route. If a wrong single is recoverable, the router no longer has to predict complexity — it only has to pick the cheapest shape that could work. That is a much easier and much more robust job, and it is the reason this ladder is the best idea in the whole design.

The chair's three decisions

The original design already had the right vocabulary. I would only pin down what each one means, because a chair that can “renew” without a definition will renew forever.

DecisionMeansUsed when

renew is bounded: a task gets at most two renewals, and each one must change the cast or the roles. A renewal that changes nothing is a continue in disguise, and the chair is not allowed to disguise it.

The chair needs an exit too

The original ladder only goes up. Three cases where the chair itself must stop:

  • The chair loops. Same guard as a run: fingerprints, then a judge, then a cap. A chair that has re-cast twice and is still planning is stuck.
  • The cast cannot cover the contract. No participant can address one of the acceptance checks — the discussion is refused rather than run and failed.
  • The chair is over budget. It reports what it has, with the unresolved objections, and the host moves the task to blocked. It does not silently truncate.

Where the person's message goes

Three layers and no obvious entry point is a real hole. The rule: the person always talks to the host, and their message is an event like any other (§14 Waking). The task's mid-run policy decides what happens to it:

orchestrated, mid-rounda claim in the discussion log, addressed to the chair, read at the next round boundary
parkedthe answer to whatever it waits on, if it matches; else a note for the resume

Discussion

In shortA chair casts up to four participants who argue in one shared log for at most three rounds. Each reads only what concerns it. A discussion never has authority of its own.

A handoff is sequential: one sender, one receiver, one answer. A discussion is the other shape — several participants at once, several rounds, a chair that judges. It is the reason to have more than one harness at all, and the easiest feature to build badly.

The chair proposes the cast; the contract validates it

The chair designs a role and a brief for each participant — that is more flexible than the fixed stances I had, because the chair can see what this particular task needs. But a chair left unchecked will cast four versions of itself, and the discussion becomes expensive agreement.

So the cast is checked before a round runs:

RuleWhy
coverage — every acceptance check has at least one participant whose role can address it otherwise the discussion runs, ends, and fails a check nobody was asked about
distinctness — no two participants share a role and a brief duplicated participants produce agreement, not information
independence — at least one participant is not on the harness that did the work the worker never verifies its own work
size — at most four cost, and a fifth voice adds no information a fourth did not

A cast that fails coverage is refused, not run and failed. That is the difference between a discussion that cannot answer and one that answers wrongly. 

interface Discussion {
  taskId: string;
  question: string;                 // the one thing being decided
  participants: {
    harness: string;                // from the catalog, probed
    route: Route;
    role: string;                   // designed by the chair, validated by coverage
    brief: Brief;
    covers: string[];               // the acceptance checks this role is responsible for
  }[];
  maxRounds: number;
  renewals: number;                 // at most 2
  budget: { minutes: number; cost: number };
}

Participants talk to each other — into a shared log

Direct address is right: a participant that must route every question through the chair is doing telephone, and the chair becomes a bottleneck that cannot answer. But a private side channel is wrong: the chair has to judge continue / renew / end from something, and the ledger has to be able to reconstruct what happened.

Direct address, shared record. A participant may ask another participant anything. Every message is written to the discussion log as a claim with from, to, kind: question | answer | objection. The chair reads the log, not a summary of it. Nothing is private; only the addressing is direct.

A claim is a reference plus a short text, not a pasted transcript. When a participant needs the detail behind a claim, it opens the file or the ledger entry the claim cites. Each participant's own conversation stays in its own harness (§18 Context).

The log is also what bounds a pair: at most two messages between the same two participants per round, then the chair is told. Two agents that like each other will otherwise talk until the budget is gone.

What each participant reads. A participant reads the claims addressed to it, the chair's one-paragraph round summary, and the claims it cites, not the whole log. Only the chair reads the full log. A claim is capped at 800 characters and cites evidence by path or id instead of pasting it. That keeps the cost of a round proportional to the number of participants instead of its square. maxRounds defaults to 3.

Who concludes

The original design had “a bot will conclude and give messages to the chair”. That is self-verification: the participant that argued hardest is the one summarising what was decided.

Instead, three steps, each with a different owner:

  1. The chair synthesizes. It already holds the log, so no extra run is needed. But the synthesis must cite claims by id — every sentence in the answer points at a claim, and a claim with no evidence is dropped rather than asserted.
  2. A verifier checks the synthesis against the contract, on a harness that was not in the cast (§11 Discussion). The chair is a worker too.
  3. The host records it. The task moves to verifying, then done or back to working with the failure as the new brief.

How the discussion ends

First of four conditions, and the ending is recorded with which one fired. A discussion that stops because the money ran out must say so, not pretend it settled.

EndingConditionWhat is reported
settled changed == false and every objection is answered or explicitly recorded as unresolved the answer, plus any unresolved objections
budget rounds, minutes or cost exhausted the answer so far, and “this did not settle”
deadlock the same split two rounds running the split, both positions, and no decision
blocking a participant raises a constraint violation or a safety issue the objection, immediately, to the person

Note what is not a termination condition: consensus. “Everyone agrees” is the failure mode, not the goal — agents converge by agreeing with each other, which is cheap and wrong. The test is no new claim, not no dissent.

A discussion never has authority, and never has a voice. It emits a recommendation and a record of dissent. If the decision needs a person — an irreversible action, a spend, a publish — the discussion's output is the input to an approval card the host renders. Same rule as the router: the thing that deliberates does not get to permit, and by the topology rule it does not get to speak to the person either.

Participants address each other freely and the host not at all. The chair's synthesis is a report (§04 Topology): it goes up to the host, which decides whether the person sees a line, a card, or nothing.

Cost control is structural, not a nag: maxRounds is set when the discussion is created, participants are capped at four, and a round only starts if the remaining budget can pay for it. A discussion that cannot afford a round does not start one.

Verification

In shortThe worker never checks its own work. A pass needs a changed output, then checks run cheapest first, never on style. The first failure is reworked once; the second escalates.

The rule is one line: the worker never verifies its own work. Everything else follows from it.

Three layers, cheapest and strongest first

LayerRunsAnswersCost
deterministic the contract's cmd / file / test checks does it do the thing? free
independent review a different harness, given the contract and the artifacts does it satisfy the contract? one run
person an approval card is this what I wanted? one click

The review question is deliberately narrow: does this satisfy the contract, not is this good. “Is this good” invites taste; “does this satisfy the contract” invites evidence, and the contract is already written down.

Output must change

A run cannot pass by reporting old work. When a run starts, the gate records a hash of every file the task names. A pass verdict is accepted only if at least one of those files is new or changed. This check is free and runs before any other, so it costs nothing on the quick path. It follows LoopForge's artifact baseline.

Checks never fail on style. Wording, headings and layout are not acceptance criteria unless the contract names them. Rework over style is a loop that no budget catches, because each round is cheap. 

interface CheckResult {
  check: Check;
  verdict: "pass" | "fail" | "skip";
  evidence: string;     // stdout · file hash · the judge's answer · the reviewer's words
  by: "deterministic" | "review" | "person";
}

What “delivered” means

Task.status gains verifying, and done requires every check to pass. Not “the run ended without error” — that is what every other product means by done, and it is not the same thing.

StatusMeansLeaves by
needs_routethe router was unsureyou pick a shape
workinga run is activeits gate (§07 The loop)
waiting_approval · waiting_input · waiting_childparked, holding no process (§14 Waking)an inbox event
verifyingchecks are runningevery check passes, or one fails

Today's limited becomes blocked with its reason, budget or loop.

A failed check is not a restart. The first failure goes back to working with the failure as the new brief: a rework, which is the handoff machinery pointed at the same task. The session is reused if it is still live, so the rework does not re-read the whole repository. The second failure of the same check escalates (§10 Orchestration), carrying both failures. After escalation, a failure ends in failed. One rework per check is what stops a task from alternating between working and verifying forever.

Why this needs to be a run and not a mode

A verification is a task with a contract whose acceptance is the review question. That means it gets a harness, a session, a budget, a ledger row and a status — for free. A special “verify mode” inside the loop would need all of those anyway, and would not be routable to a different harness, which is the entire point.

Its verdict is a report (§04 Topology), not a message: the host turns it into a card the person can act on, or into silence when the check passed and nothing needs saying.

“What did it deliver?” is a query, not a conversation. Every CheckResult is a ledger row. You can ask a finished task what it produced, which check proved it, and who signed off — without reading a transcript.

Bounds

In shortEvery cycle stops at a number: steps, reworks, escalations, renewals, rounds, hops and wakes. One budget covers everything a task causes, and a quick task makes no extra model call.

Every cycle in this design can repeat: a run's steps, a rework, an escalation, a chair's renewals, a discussion's rounds, a handoff chain, a task's wakes. Each section bounds its own cycle, so this section collects the bounds into one table and adds the two that no single section owns: one budget for everything a task causes, and a cost ceiling for the quick path. One budget per root task

Today each turn has its own budget, so a task that hands off twice can spend three budgets, and a chair with four participants can spend five. The fix: the root task owns the only budget, in tool calls, minutes and cost. A run, a child task, a cast member, a verifier or a compaction reserves its share from the root before it starts and returns what it did not use when it ends. A reservation that cannot be made is not made: the work does not start, and the task reports what it would have needed.

Running out is never an escalation trigger. A task that runs out of budget moves to blocked and asks you to add budget or stop, because escalating would spend money you did not approve. That is the one decision in this design reserved for you.

The quick path makes no extra model call

The overhead of a router is paid on every task, so it has a ceiling of its own. A task that the rules route as single and quick runs with:

  • no router model: the rules decided;
  • no contract proposal: the implicit contract applies (§05 The contract);
  • no host model: the result is rendered from a template (§04 Topology);
  • no review run: its implicit contract has only deterministic checks (§12 Verification).

That is one model-driven run and nothing else. Any extra call must be justified by the shape or the effort, and every model call outside a run is a ledger row with its reason, so the overhead per task is a number you can read.

Why this matters more than any single feature. Over-analysis of simple tasks and loops that never stop are the two failures this design is most likely to reproduce. Both are prevented here by arithmetic rather than by asking a model to show restraint.

Waking

In shortTasks are woken by events (your message, a timer, a webhook, an answer) that queue in an inbox. A parked run costs a database row, not a running process.

Everything up to here assumes somebody typed something and is watching. That is the wrong base case for an agent that should keep working after you close the laptop. The correction is one sentence: a task is woken, not started. A person's message is one kind of event among several, and the machinery that turns events into runs is the same for all of them.

This section follows the five primitives in Anthropic's Building always-on agents — event inbox, timers, memory, permissions, outbox — adapted to a single-user router. Memory gets its own section; permissions are Policy, not argv.

The cycle

The inbox

Do not let an event source call the agent. Two events arriving together start competing runs, and a crash loses the event entirely. Instead every source writes a row and a worker pulls. 

type WakeSource =

interface InboxEvent {
  id: string;

Run and job are different things

This is the correction the always-on model forces on the design. A run is the durable attempt: it owns the session, the budget, the status. A job is one lease on the worker. A run that parks — waiting for an approval, a question, a child, a timer — has no job. Its state is a row, and the worker is free. 

// one run, three jobs, one session
run r-7  status=waiting_approval   session=s-2   // job ended at the gated call
  job 1  claimed 10:00  → gated call at 10:04, parked
  job 2  claimed 10:31  → answer arrived, resumed, posted, parked on a child
  job 3  claimed 10:52  → child settled, resumed, finished

Without this split, "pause" means "hold a process", and a paused task costs a worker slot. With it, a hundred parked tasks cost a hundred rows.

An event that arrives mid-run

The article names three policies and they are the right three. VicBot picks one per task, at creation, from the shape:

PolicyMeansDefault for
pushthe event waits in the inbox for the next runeverything — the safe default
foldthe event joins the current run at its next stepa harness with steering: true, and a person adding a detail
interruptthe run stops, and restarts with the eventan event that invalidates the work — a cancelled ticket, a changed requirement

This is also the answer to “where does the person's message go” (§10 Orchestration): it is an event, and the policy decides whether it steers, queues, or stops the work.

Timers

Timers are what make a task proactive rather than merely resumable. Two kinds, one store, and — importantly — a timer never starts a run. It enqueues an event; the inbox does the rest. 

interface Timer {
  id: string;
  taskId: string;
  kind: "follow-up" | "schedule";
  dueAt: number;
  cron?: string;          // schedule only
  note: string;           // why this wake exists, in the agent's own words
  status: "armed" | "fired" | "cancelled";
}

The store is separate from the inbox, and the inbox only holds ready events. That separation is what stops a one-minute schedule from flooding the queue: the scheduler polls, fires what is due, updates the timer, and only then writes one event.

Each occurrence of a schedule is a new child task of one standing task that owns the timer. Every occurrence gets its own budget, record and result, and the standing task holds the history, so “what did the 9am job do last Tuesday” is one lookup.

The outbox, and the right to say nothing

A watched agent streams. An unwatched agent has to decide whether to speak, and the decision is part of the product. The outbox has exactly one writer: the host bot (§04 Topology). An execution bot that wants something said files a report; the host decides what reaches the person.

How a run endsWhat happens

silencenothing is delivered, and the ledger records that the run chose not to speak
defera request for a person — an approval or a question — goes out, and the run parks

Silence being a first-class outcome is the difference between an assistant and a notification generator. The rule I would ship with: start quiet, and earn attention. A new task's default is to report only when it is done, blocked, or wrong — not on every step. And because the host is the only writer, “quiet” is one decision in one place rather than a policy every bot has to remember.

Deferred calls

This is how an unattended run asks for permission without holding a worker. It is the same mechanism as the loop's waiting_approval, described from the wake side:

  1. A gated tool call is reached. The run parks: status waiting_approval, the pending call's id and input saved, the job released.
  2. The request goes to the outbox as a defer — or straight to the UI if somebody is watching.
  3. The person answers. Their answer is an event in the inbox.
  4. A new job claims the run, resumes the session with the decision, and the turn continues.

While it waits, the worker serves other tasks. A parked run with no answer for a day is not a leak — it is a row with a deadline, and the deadline is a timer.

Interactive and unattended are a mode, not a product

VicBot is a coding router; most of its tasks are watched. Always-on is something a task enters, not the base state of the product. So the mode is a field on the task, and it can change mid-life — you close the laptop and the task becomes unattended.

ModeDeliveryApprovalsDefault for

The mode changes three defaults and nothing else. The loop, the policy table, the contract and the ledger are identical — which is the point: an unattended task is not a second product.

Session

In shortWhen a harness session is lost, VicBot rebuilds from a recovery block and says so. A resumed session receives only what is new since its last turn, including the policy.

VicBot already has the right primitive — sessionId on the task, resume in RunSpec. What it lacks is a contract for when the session is gone, which is the case that actually happens: a cleaned /tmp, a new machine, a harness upgrade that invalidates its own store. 

type SessionState = "live" | "lost" | "closed";

interface Recovery {

  contract?: Contract;       // so the new session knows what done means

  note: string;              // "the previous session was lost; this is a fresh start"
}

Resume or start fresh

Every wake makes this choice, and the rule is the article's: an event that continues earlier work resumes the session; anything else starts a new one.

Two details worth stealing outright. First, reassert the policy on every turn — a resumed native session can otherwise keep a stale, more permissive mode. Second, keep two clocks: when the task started, and when the current stretch of work started. A run that posted and came back from an approval was reporting minutes of “thinking” that never happened.

A resumed session gets a delta, not the bundle (§18 Context): only what happened since its last turn. The policy reassertion above is part of that delta, so it is never skipped.

The promotion test, in one sentence: would this still be true for the next task? If yes it belongs in long/; if it is only true for this one, it stays in short/ and is eventually archived.

One fact per file

A note is a key and a value, not a line in a log — so the file is the key. Writing a fact again rewrites its file. That gives atomic upsert (temp + rename), a diff per change, and a greppable store, without a schema.

---
key: prefers-tabs
kind: note

writtenBy: task t-7f3a / run r-9c
at: 2026-11-14T09:12:00Z
supersedes: null
---

The front-matter is what the index is built from, so index.db can be deleted and regenerated at any time. The body is what a person reads and what a harness greps.

The manifest

The manifest is the answer to “how does another agent find the memory it needs”. It is not a listing of every fact — that would grow without bound and be stale by Tuesday. It is the schema and the conventions: where things live, what the rules are, how to search.

It has two parts, and they have different owners:

PartOwnerContents
preamblethe keeper, authoredthe layout, the rules, how to search — stable, cached, ~50 lines
indexderived from diskfolder counts and the last curate pass — small and bounded
 
--- memory/manifest.md ---
# Memory

This folder is VicBot's memory. Read this file first.

## How to find things

- long/instructions.md — how the person wants you to work.
  Loaded every wake; read it in full.
- long/notes/<key>.md — one fact per file, keyed by filename.
  Grep this folder, or call recall(query).
- short/<task-id>/progress.md — what that task has done and what is left.
  Read your own task's file; do not read another task's.
- short/<task-id>/told.md — what that task already told the person.
- archive/ — superseded. Never loaded. Kept for the record.

## Rules

- Write when you learn, not when you finish.
- One fact per file. If a fact changes, rewrite the file.
- If it lives in the repo, store a pointer, not a copy.
- Never delete. Archive.

## Index (generated — do not edit)

long/instructions.md            14 lines
long/notes                      37 files
short/                          3 open tasks
archive/                        2 months, 41 tasks
last curate                     2026-11-14T03:00Z  ·  4 promoted, 9 archived, 2 merged

A harness with no recall tool can still find memory, because the manifest tells it the paths and its own grep does the rest. That is the degradation story for memory, and it is why the manifest is prose rather than a schema.

Concurrent writes

Two tasks writing at once is normal, and the layout makes it boring: one fact per file means different facts are different files. The same key written twice is last-write-wins, and both writes are ledger rows, so the overwrite is visible rather than mysterious. Writes go through temp + rename; the index is updated incrementally on write and marked dirty; the keeper does the full rebuild.

What the bundle gets

Every wake loads manifest.md (stable, cached), the task's own short/<task-id>/progress.md (volatile), and nothing else. Details arrive through recall() or the harness's own file tools. That is the context budget, applied to memory.

Memory is not the ledger. The ledger is append-only and never edited; memory is curated and routinely rewritten. A run that reads memory is reading a summary; a run that needs to know what actually happened reads the ledger.

The keeper

In shortA scheduled task curates memory. It archives, promotes and tidies, never deletes, asks you when two notes disagree about what you want, and never wakes itself.

Memory that is only written by the run that needed it accretes contradictions, dead ends and facts about code that no longer exists. Something has to curate it, and that something should be always on — it is the one job in VicBot that is genuinely continuous.

In the product it is a specialized bot with a name and a job. In the architecture it is a scheduled task (§14 Waking) with a fixed brief and a contract — which means it gets a harness, a budget, a session and a ledger row like everything else, and needs no new machinery.

It never speaks to the person. Its output is a report (§04 Topology) — “4 promoted, 9 archived, 2 merged, 1 contradiction needs you” — and the host decides whether that is a line, a card, or silence. A keeper that files a report every day is a keeper the person will mute.

Five jobs — four that act, one that reports

JobDoesNever
clean a task's short/ folder is archived when the task is done and quiet for N days, or failed and unlooked-at; scratch/ goes, progress.md is promoted or archived touch a task that is still running
promote a fact in facts.md that passes the test — would this still be true for the next task? — moves to long/notes/<key>.md promote anything without writtenBy and at
tidy merge duplicates, resolve contradictions (newer wins, the supersession is recorded), turn copies into pointers, archive notes whose referent is gone resolve a contradiction by deleting one side
manifest regenerate the index section; rewrite the preamble when the layout or the rules changed let the index describe a file that is not on disk
report does not decide surface contradictions it cannot settle as a question — two notes that disagree about intent, not about a fact pick a winner between two notes that disagree about what the person wants

The fifth job is the one that keeps the keeper honest. A contradiction about a fact has a right answer — the code moved, the note is stale — and the keeper settles it. A contradiction about intent does not: two notes that say different things about how the person wants to work are evidence that the person changed their mind, and only the person can say which one is current. So the keeper surfaces it as a question and leaves both notes in place until it is answered.

The thing that maintains does not get to decide what is true — the same rule as the router and the chair, applied to memory. A keeper that resolves an intent contradiction by choosing the newer note is a keeper that silently overwrites the person's preferences.

Its contract

The keeper is a task like any other, so its definition of done is a contract (§05 The contract) — and it is the one contract in the system that is entirely mechanical: 

acceptance:
  - cmd:  every file named in manifest.md exists on disk
  - cmd:  every file on disk is named in manifest.md
  - cmd:  no note under long/ has a mtime older than the file it points at
  - cmd:  no two notes share a key
  - judge: "do any two notes contradict each other?"
  - judge: "does every short/ entry belong to a task that is still open?"
constraints:
  - never delete; archive
  - never write outside memory/
  - never touch a task that is still running

The first four checks are free and catch almost everything. The two judge questions are the ones a script cannot answer, and they are exactly the two that keep memory from rotting in place.

Its policy

The invariant that makes it safe

The keeper cannot delete, only archive. Every removal is a move to archive/<month>/, every change is a ledger row, and the contract checks that every archived fact is still readable. Memory is allowed to be wrong; it is not allowed to lose something silently.

That is the memory equivalent of the ledger being append-only, and it is what lets the keeper be aggressive. A conservative curator leaves rot; a bold one that can delete is unshippable. One that can only archive is both.

When it runs

Time is the wrong trigger — a quiet week needs no curation and a busy afternoon needs three passes. So the schedule is a floor, and the real trigger is an event:

TriggerKind
every 24 hoursa floor, so a quiet install still gets tidied
every 20 completed tasksa count — enough new material to be worth a pass
a task archivedan event — its short/ folder is now a candidate
a contradiction reported by a runan event — a run that finds two notes disagreeing says so, and the keeper is woken. The keeper's own runs are the exception: their contradictions go to you, so the keeper cannot wake itself

All four are events in the inbox (§14 Waking), so the keeper is not special-cased in the wake layer — it is a task whose timers and events happen to be about memory.

Why it is worth having at all

Because the alternative is worse in a way that is hard to see. Without a keeper, memory grows monotonically, contradictions accumulate, and every wake pays for an index that is increasingly noise. The failure is not a crash; it is an agent that slowly gets vaguer. A curator with a mechanical contract is the cheapest defence against that, and it is the only always-on job in VicBot that pays for itself in tokens saved.

Context

In shortThe harness keeps its own transcript; VicBot never copies it. A first run gets a fixed-size bundle, a continuing run gets only a delta, and rework gets a five-field block. Outside text and peer messages are wrapped as untrusted.

Memory is what persists. Context is what gets assembled for one wake and thrown away. They are different problems with different failure modes — memory rots, context overflows — and the design only works if they are kept apart.

Five layers, five lifetimes

ledgerforever, append-onlyVicBotnever — read on demand

The boundary that matters: the ledger is never in the prompt, and the transcript is not memory. Everything else follows.

The budget is allocated, not discovered

A context window is not a place to put things until it is full. Each layer gets a named allocation, and the allocations are the design:

The percentages are illustrative and the shape is not: the fixed part is over a third of the window before the task says anything. That is why the next subsection matters more than any retrieval trick.

The transcript stays with the harness

Each harness already keeps its own conversation and can resume it by session id. So VicBot never copies a transcript, never re-sends one, and never summarises one to build a prompt. A continuing run resumes the native session and receives only what is new since its last turn. The ledger keeps references (the session id, a cursor, the files touched), not copies of the conversation.

WakeWhat the prompt contains
first run of a taskthe full bundle
a continuing run, session livea delta: the new events, any changed contract section and the clock; the stable prefix is already in the native session

This is the cheapest context rule in the design, and it comes from AutoSwarm, whose records “never copy native full histories”. It also removes most of the need for compaction: a live session already manages its own window, and VicBot only has to keep what it adds small.

The stable prefix

The VicBot-owned part of the stable block has a ceiling of its own: about 1,500 characters for the rules, limits and verdict instructions, before tools and memory. AutoSwarm's whole communication block is about 1,100 characters. A rule that does not fit there belongs in a check, not in the prompt.

Prompt caching is the only cost lever that compounds. It works when the start of the prompt is byte-identical across calls, and it fails silently when it is not. So the rule is blunt:

Anything that varies per wake goes after the last cache breakpoint. The system prompt has no timestamps, no run ids, no task ids and no “today is”. The clock lives in the first user turn, where it belongs and where it costs nothing.

the memory index, sorted by keythe working set
the harness's own guidancethe transcript tail

Three breakpoints fall out of that: after the fixed block, after the semi-stable block, and before the volatile block. A wake that changes only the working set re-uses two of the three.

The bundle and the projection

This is where a multi-harness router differs from every reference. A harness's context is not portable: omp takes --append-system-prompt <file>, Codex reads an AGENTS.md from the working root, dsh takes a profile and a stdin preamble, a stdio harness takes JSON. If the assembler wrote any of those directly, the design would be welded to three CLIs again — the same mistake as HarnessId.

So assembly produces a harness-neutral bundle, and each adapter projects it:

interface ContextBundle {
  // stable
  identity: string;              // who you are, what VicBot is, the nine rules
  tools: ToolSpec[];             // from the gateway, sorted
  // semi-stable
  contract: Contract | null;
  memoryIndex: string;           // keys and titles, sorted
  // volatile
  progress: string;              // this task's own note
  events: InboxEvent[];          // what woke this run, enveloped (see "The inbox is an injection surface")
  workingSet: string[];          // artifacts, claims, recent results
  clock: string;                 // the only place a time appears
}
HarnessProjection
omp / pirendered to markdown, written to a file, passed as --append-system-prompt <path> — a path, not inline text, because a 20k-char prompt blows the Windows spawn budget
codexa generated AGENTS.md fragment in the working root, removed when the run ends

The adapter may re-render, never edit. It cannot add a fact, drop a section or reorder the contract. A test asserts that every required section of the bundle appears in every projection — which is the only way to keep four projections honest without reading four prompts.

What crosses a handoff

A handoff to a different harness is a deliberate context reset with a payload, not a transfer. The new harness has no session, and pretending otherwise produces a 200k-token prompt that says nothing.

The brief is the compression. That is why it is typed and capped rather than free text: a handoff is the one place where a summary has to be good, because it is all the receiver gets.

Compaction is a run

When a session exceeds its allocation there are three options, and two of them lose detail. So the loss is made explicit and auditable rather than incidental:

  1. only when the harness cannot: a live session compacts itself, so this applies to a session with no native compaction or one that has failed with an overflow;
  2. persist first — a compaction run reads the transcript and writes progress and told;
  3. then compact or restart — the next wake starts a fresh session from the bundle;
  4. then check — a judge check asks: given this summary and the contract, could you continue? A summary that fails is redone once; if it fails again, the summary is dropped and the next session starts from the recovery block (§15 Session).

Compaction being a task means it gets a cheap harness, a budget, and a ledger row. It also means the person can read what was thrown away, which is the difference between compaction and forgetting.

The rework block

A rework or retry turn gets one fixed block with five fields, so the run does not have to rediscover why it is being asked again: 

## Rework (attempt 2 of 2)
Failure:  the exact failed check or verdict reason, capped at 4,000 characters
Action:   what must change, from the check or the reviewer
Previous: the first 1,200 characters of the last answer
Files:    the paths the last attempt touched
Session:  resumed (or: fresh, because the session was lost)

The block replaces “try again”. AutoSwarm v1's recovery context and LoopForge's retry feedback use the same shape: carry the concrete failure forward instead of the conversation.

The inbox is an injection surface

A webhook body, an issue description, a PR comment, an email — every one of them is written by somebody who is not the person, and every one of them reaches the model. An always-on agent therefore has a permanent, unattended prompt-injection surface that an interactive agent does not.

Every event payload is untrusted by default. It enters the prompt inside an envelope that names its source and its id, and the rules say that text inside an envelope is data, never instructions. The envelope is applied by the assembler, not by the harness, so a third-party harness cannot forget it.

<external source="webhook:github" id="evt-8812" trust="untrusted">
  body text, size-capped, with any nested envelope markers escaped
</external>

Two details that matter more than they look. Escape the markers, or a payload can close its own envelope and speak as the system. Cap the size, and record the cap in the ledger, because a truncated payload that looks complete is worse than a refused one.

Messages are envelopes too, and silence is the default

A message from a peer or from the person, delivered into a live run, enters inside its own envelope naming the sender and the message id. Peer text is collaboration input, never new authority: it cannot grant a permission or change the task. Every message also carries one fixed rule:

Every reply wakes its recipient. Reply only when a message asks you something or needs your decision. Do not acknowledge status updates, completion notices or other acknowledgements. A reply is not the end of your assignment: answer, then continue.

The rule is AutoSwarm's, nearly word for word. Without it, two polite agents spend their budget thanking each other. It costs one sentence and it is the cheapest loop guard in the design.

Enforced, not hoped for

Assembly ends with a measurement, not a guess. fitContext() counts the projection and, if it is over the allocation, cuts in a fixed order — working set first, then the transcript tail, then refuse: 

// the cut order is part of the contract
1. drop working-set items, oldest first, recording what went
2. drop the transcript tail back to the last complete tool exchange
3. still over → fail the run with "context_overflow", never truncate the system block

Every cut is a context step in the run's trail, so “why did it forget that?” has an answer that is not a guess. And the system block is never a candidate: a run that silently loses its rules is worse than a run that fails.

Deployment

In shortVicBot runs as a server with no public port. You reach it through a private network from paired, scoped devices: a web app, the CLI, push and later a chat bridge. Clients hold no state.

VicBot ships as two things: a server that does all the work, and clients that let the person reach it from anywhere. The server runs on a machine that stays on. A client is a window onto it: closing one loses nothing, and any client can pick up where another left off.

What lives where

On the serverOn a client
tasks, runs, sessions, the ledger, the inbox and outboxa device token, and a cache it can drop at any time
every harness CLI, its login and its API keysnothing: a client never sees a harness credential
workspaces and repositoriesfiles the person chose to upload or download
memory/, timers, schedulesthe person's notification settings for that device
the policy table and every decision it makesthe person's answers, sent as events

That split is rule 9 in practice. It is also why running on a server costs the rest of the design almost nothing: Waking already assumes nobody is watching, and the mailbox already has exactly one writer (§04 Topology). A client is one more reader of the outbox and one more source of inbox events.

The server has no public port. Agents on it run unattended with write access and real credentials, so the cost of a mistake in authentication is everything on the server. The person reaches it through a private network the person controls:

Whatever carries the traffic, the gateway still checks every request (below). The network is the first wall, not the only one.

Devices, not accounts

There is one person, so there are no accounts. There are devices. A new device is paired once:

  1. On a device that is already paired, or on the server itself (vic pair), the person asks for a pairing code. It is valid for five minutes and for one use.
  2. The new client presents the code and receives a device token: a random secret, stored on the device, sent with every request. The server stores only its hash.
  3. The device appears in a list with its name and last-seen time, and can be revoked from any paired device or from the server. Revoking takes effect on the next request.

An approval card for an irreversible action is shown everywhere but answerable only from a full device. A lost phone can then cancel and confuse, but not ship.

The gateway

The gateway is the only thing a client talks to, and it does three jobs: authenticate the device, check its scope, and translate between the client API and the server's inbox and outbox. It never runs work itself.

Every call carries the device token. Writes also carry an idempotency id, so a phone that loses signal and retries does not start a task twice. Origin and host checks stay in place for browser clients. Every call is a ledger row with the device as its source (§21 Events & ledger).

Offline, reconnect, and two devices at once

  • Reconnect is a cursor. A client remembers the last outbox position it saw and resumes from there. Nothing is lost while it was away, because the outbox is on the server.
  • Offline writes queue on the device with their idempotency ids and are sent on reconnect. An answer that arrives after its card was already answered elsewhere is rejected with “already answered on device”, never applied twice.
  • The first answer wins. A card answered on the laptop disappears from the phone on its next update. Answers are compare-and-set on the parked run, like every other transition (§07 The loop).
  • Notifications follow attention. When a client is open and the task is on screen, push is not sent for it. Otherwise the outbox's pacing rules decide (§14 Waking).

Work that needs the person's machine

Some work cannot happen on a server: using a desktop app, a browser where the person is signed in, or a file only on the laptop. The operate route meets this first. The answer is an execution node: a small agent the person runs on their own machine, paired like a device, that dials out to the server and accepts runs for one route. It is a harness location, not a client. It runs under the same policy, budget and ledger as any run (§20 The harness boundary). Without one, a task that needs the person's machine asks for it instead of failing silently.

Execution nodes come after the server and the first two clients. LoopForge's connected execution machines show the same need.

The harness boundary

In shortA harness is a manifest plus a process speaking a JSON-lines protocol, and every harness runs on the server. Features degrade when a capability is missing instead of requiring it.

Today this is the weakest part of the design, and the first thing I would change. HarnessId is a closed union — "dsh" | "omp" | "codex" — and ROUTE_HARNESS is a hardcoded map from route to harness. A fourth harness means editing the type system, the config, the registry and the UI. That is not a boundary; it is a switch statement with good manners.

The fix: a harness is a manifest plus a process that speaks the event protocol. Nothing about it is in VicBot's source. 

// harness.json — what a harness author writes
{
  "id": "my-harness",
  "name": "My Harness",
  "protocol": "1.2",                 // semver; the major is negotiated at handshake
  "entry": { "kind": "stdio", "cmd": ["my-harness", "--vicbot"] },
  "probe": ["--version"],
  "capabilities": {
    "approvals": true,
    "steering": false,
    "resume": "cursor",            // "cursor" | "none"

    "sandbox": ["read-only", "workspace-write"],
    "images": false

  "routes": ["build"],             // only what it can actually serve
  "cost": "subscription"
}

Every feature checks a capability and degrades, rather than requiring it. If it cannot degrade, it does not belong in the product.

Every harness runs on the server, under the server's accounts and credentials (§19 Deployment). A harness feature that needs the person's own machine, such as a GUI, a browser profile or a local login, is a degradation to plan for, not an exception.

What is still entangled, and cannot be fixed

One thing, honestly: a pause/resume cycle needs the harness to keep something. A harness with resume: "none" can still pause and resume, but the resumed run starts from the recovery block — the task survives, the context does not. That is a real cost and it should be shown to the person, not hidden.

Events and the ledger

In shortThe event union gains approval, steering, claim and check events. Wake events get their own union, and the ledger records who started every action.

VEvent is the right idea — one harness-neutral union — and it is missing seven things that the references have or that the shapes above need. Adding them is cheap now and expensive later. This union is also the wire format for a stdio harness, so it has to be complete enough that a third party never needs a side channel. 

type VEvent =
  // … today's: user route session text thinking tool usage notice error limit handoff exit
  | { kind: "approval"; id: string; tool: string; input: unknown;
      phase: "asked" | "decided"; decision?: "allow" | "deny" }
  | { kind: "steer"; text: string; phase: "sent" | "read" }
  | { kind: "session"; id: string; state: "live" | "lost"; note?: string }
  | { kind: "handoff"; direction: "to" | "from"; taskId: string;

  | { kind: "claim"; discussionId: string; from: string; to: string | null;

      text: string; cites?: string[] }        // the shared log (Discussion)
  | { kind: "check"; taskId: string; check: Check;

  | { kind: "usage"; input: number; output: number; cost?: number;

Two unions, not one

VEvent is what happens inside a run, and it is the wire format for a harness. The wake layer needs its own, smaller union, because a harness must never be able to invent an inbox event: 

type WakeEvent =
  | { kind: "enqueued"; event: InboxEvent } // Waking
  | { kind: "claimed";  eventId: string; jobId: string }
  | { kind: "batched";  eventIds: string[] }        // several became one wake
  | { kind: "timer";    timerId: string; phase: "armed" | "fired" | "cancelled" }
  | { kind: "out";      messageId: string; phase: "queued" | "sent" | "suppressed" }
  | { kind: "parked";   runId: string; on: "approval" | "input" | "child" | "timer" };

Every ledger row carries an initiator: person, schedule, webhook, handoff, discussion, verify, retry, resume. That single column is what lets you ask “what ran while I was away”, which is the first question anyone asks of an agent that works unattended — and with Waking it becomes answerable by query instead of by reading transcripts. Rows a person causes also record the client they came from, so an approval given from a phone is distinguishable from one given at a desk.

Migration

In shortTwenty-one steps from today's code to this design, each shippable on its own, and the order constraints between them.

Twenty-one steps, each one shippable and each one testable on its own.

  1. Split the tables. tasks → tasks + runs + sessions. Backfill: one run per task, one session per task. Nothing else changes yet, so the UI still works.
  2. Move the process into the adapter. Harness.spawn() returns a handle. The three adapters keep their current argv; only the ownership of the child moves. This is the riskiest step and the one that unblocks the rest.
  3. Extract policy.ts. The argv builders stop containing trust decisions. A test asserts that no adapter constructs a sandbox flag itself.
  4. Add the verdict and output baselines. A run ends by writing .vicbot/verdict.json; the gate hashes named files at start and rejects a pass with no changed output. Replaces today's <handoff> regex. Cheap, and it fixes the weakest part of today's code.
  5. Open the boundary. Replace HarnessId with string, add the manifest, the registry and the stdio loader. Ship with the three first-party manifests. Add the null-harness test — the whole suite against a harness that can do nothing.
  6. Add waiting. A run can pause and resume. Wire one harness's native approval channel first and leave the others on never.
  7. Run it as a server. The gateway with device pairing, tokens, scopes and idempotency ids; vic serve as a system service on a local-disk data directory; a private-network setup guide. The web UI and vic CLI become clients of /v1. Nothing else changes underneath.
  8. Add the host and the shapes. Three shapes at intake, the status machine, the root budget, the ceilings in Bounds, and the escalation triggers — still with a single bot doing the work. No chair yet. This step alone is worth shipping: it is where a failed task stops being a dead end.
  9. Add the contract and checks. A task may carry one; verifying becomes a status; deterministic checks run first. Independent review comes after.
  10. Add the chair and the cast. Split, coverage check, shared log, four endings, continue / renew / end. The chair is a run like any other, so nothing new is needed underneath it.
  11. Split run from job. A run becomes a durable row; a job is the lease. Nothing else changes yet — the loop still runs to completion — but a parked run now costs a row instead of a process. This is the step that makes everything after it cheap.
  12. Add the inbox and the worker. Every trigger becomes an event: the person's message first, then child settlement and check results. Dedupe, batch, one active job per task. The CLI now writes to an inbox instead of calling the loop.
  13. Add the outbox. A run ends by sending, staying silent, or deferring. Silence becomes a recorded decision. Delivery is paced from quiet.
  14. Add push and the PWA shell. Web Push or ntfy for cards and results, offline queueing with idempotency ids, first-answer-wins on cards.
  15. Add timers. Follow-ups and schedules feed the inbox. No memory yet — a timer that wakes a task with no memory is still useful, and it is the smaller step.
  16. Add the memory folder. short/ and long/, one fact per file, the manifest, and index.db as a rebuildable cache. Ship the invariant first: every file on disk appears in the manifest, and every manifest entry exists.
  17. Add the keeper. A scheduled task with the mechanical contract, archive-only, writableRoots: ["memory/"]. Run it in dry-run for a week and read its diffs before letting it write.
  18. Add the bundle and the projection. Assembly produces a harness-neutral bundle; each adapter renders it. Ship with the invariant test — every required section appears in every projection — before adding a fourth harness, not after.
  19. Add the budget and the envelope. Named allocations, fitContext with a recorded cut order, and untrusted enveloping for every event payload. This is the step that makes a webhook safe to accept.
  20. Add a chat bridge and execution nodes. Telegram as a standard device; an execution node for work that needs the person's machine. Both after the envelope, because both carry text from outside.
  21. Split the ledger. Transcript becomes rebuildable; the ledger becomes append-only with initiator. Last, because nothing depends on it.

Order matters. Moving the process into the adapter (2) comes before adding waiting (6), because an approval you cannot answer is worse than no approval. Extracting the policy (3) comes before opening the boundary (5), because a third-party harness must never choose its own trust. The verdict (4) comes early because escalation (8) and checks (9) read it. Running as a server (7) comes before the inbox (12), so remote clients exist before there is anything for them to wait on, and after waiting (6), so an approval from a phone has something to answer. Opening the boundary (5) comes before the contract (9), because a contract is only meaningful if the thing executing it is interchangeable. The host and shapes (8) come before the chair (10), because the chair is only worth building once a single run can already escalate. Splitting run from job (11) comes before the inbox (12): an inbox in front of a loop that cannot park is a queue that fills up and stalls. The envelope (19) comes before the chat bridge (20) and before any webhook source, because both put outside text into the prompt.

Risks

In shortWhat can go wrong, how bad each failure is, and the mitigation for each.

RiskHow badMitigation
The harness's own compaction drops something VicBot relied on. A long native session summarises itself, invisibly. medium: the run works to a half-remembered contract the contract and the verdict instructions are re-sent in every delta, so they never depend on the native transcript; checks run against files, not memory
The server is reachable by the wrong person. It runs agents with write access and real credentials. high: everything on the server is at stake no public port; a private network first; device tokens stored hashed, scoped and revocable; irreversible approvals only from full devices; every call a ledger row with its device
A lost or stolen device. medium: bounded by its scope revoke from any other device or the server; a phone defaults to standard, so it cannot approve an irreversible action
The data directory is on a network filesystem. SQLite locking is unreliable there. high: silent corruption vic serve checks the filesystem type at start and refuses to run on NFS or SMB
Overhead swamps small tasks. A one-line request pays for a contract proposal, a router model, a host summary and a review run. high: it is the first thing a user notices the quick path makes no extra model call (§13 Bounds); every non-run model call is a ledger row with its reason, so overhead is measured per task
Harness event drift. Every harness is a JSON dialect, each free to change. high — it is the whole adapter layer a recorded-fixture test per harness, replayed in CI; a protocol major negotiated at handshake; a probe that fails loudly rather than silently mis-parsing
A third-party harness is hostile. It gets a working root and a budget. high — arbitrary code with your files the stdio loader runs under the same policy as a run; a harness cannot raise its own trust; the default for an unknown manifest is read
Handoff thrash. A→B→A→B on a task neither can finish. medium — costs money, looks broken depth cap, a per-task hop budget, and “a handoff may not target the task that handed to you”
The chair is a single point of failure. It loops, or its cast cannot cover the contract. medium — the whole orchestrated shape depends on it the same loop guard as a run; a coverage check that refuses a bad cast; an exit to blocked with unresolved objections rather than a silent truncation
Escalation becomes the normal path. Everything ends up at the chair. medium — it is the expensive shape escalation requires evidence; the ledger counts how often each trigger fires, and a rising rate is a router bug, not a feature
Discussion becomes expensive theatre. Four agents agreeing for six rounds. medium — the most quotable failure mode coverage and distinctness on the cast, structured claims, budget checked before a round starts, a hard four-participant cap
Pause/resume bugs. The classic: a resume that re-runs a side effect. high — silent, and it corrupts real state the resume carries the decided call's id and result; a tool call executes at most once per (run, callId), enforced in the store, not in the loop
The contract is wrong. Checks that pass while the goal is unmet. high — false confidence is worse than none the contract is shown before work starts; a judge or human check is mandatory when the goal is not mechanically checkable
A task wakes forever. A schedule that keeps failing, a follow-up that re-arms itself. high — it spends money with nobody watching a per-task wake budget (count and cost, not just time); a task that exhausts it moves to blocked and stops arming timers until a person looks
Notification fatigue. The outbox becomes a feed. medium — it is how always-on products get muted start quiet; silence is the default ending; the ledger counts sends per task per day and the number is visible before it becomes a complaint
A parked run is forgotten. Nobody answers the deferred call. medium — the work silently stops every defer arms a timer; when it fires with no answer, the run resumes with “nobody answered” and the task decides whether to proceed, wait, or block
Memory rots. Notes contradict the code they describe. medium — worse than no memory, because it is trusted the pointer rule; the curation task with a real contract; and memory is never the record — the ledger is
Cache misses that nobody notices. One timestamp in the system prompt and every wake pays full price. medium — silent, and it compounds the stable-prefix test: render the bundle twice a minute apart and assert the first two blocks are byte-identical
A projection drifts. One adapter quietly stops including the contract. high — the run then works to the wrong definition of done the invariant test over every projection, run in CI against the null harness too
Compaction forgets something load-bearing. high — it looks like the agent got worse persist before compacting; the judge check; and the compaction is a task whose output the person can read
The host is a bottleneck and a single point of failure. Every message and every report passes through one bot. high — nothing reaches the person without it the host is stateless per turn: it reads the task row and the mailbox and holds nothing between turns, so it restarts freely; its own loop guard applies; and a report that cannot be summarised is delivered verbatim rather than dropped
The host becomes a lossy summary layer. The person only ever sees the two-sentence version. medium — it degrades trust slowly every summary carries a pointer to the full report in the ledger; compression is allowed, truncation is a bug
The keeper is too aggressive. It archives something that mattered. high — memory loss is invisible until you need it archive-only, never delete; dry-run for a week; every change a ledger row; and the contract check that every archived fact is still readable
The manifest drifts from disk. It describes a layout that no longer exists. medium — every agent that reads it is misled at once the two-way check in the keeper's contract, run on every pass and in CI on a fixture folder
Scope creep toward a platform. high — it is how all four references got to 1M+ lines the non-goals table is a review checklist; a feature that needs a new table needs a paragraph in “What we don't build” first

Two things I would protect above everything else: the task outlives the harness, and a cheap shape can always become an expensive one, carrying its evidence. Every other decision here can be revisited. Those two are the product.

Open questions

A living document should say what it does not know. These are the decisions still owed:

  • Whether the host's templates cover enough. The target is no host model call on the quick path. Whether templates cover enough reports is measured, not argued: a week of the ledger's host-call count answers it.
  • The default budgets. The numbers in config.ts (3, 15 and 60 minutes; 15, 80 and 300 tool calls) are first guesses from the current code and need a week of real tasks.
  • Whether steering is worth building early. fold needs a harness that accepts a message mid-turn. omp has an RPC mode; whether Codex and dsh can do the same is not yet checked.
  • Which private network to document first. A WireGuard mesh is the default, but which product (Tailscale, Headscale, plain WireGuard) depends on what the person already runs.
  • Where the operate route runs. Codex on a headless server cannot use the person's desktop. Until an execution node exists, computer-use tasks either run in a server-side browser or ask for the person's machine.
  • One server or several. The design assumes one. A second server, say a GPU machine, would be an execution node, not a second VicBot.

Resolved in v0.7: where the chair's budget comes from (§13 Bounds), whether a schedule creates or resumes a task (§14 Waking), how the keeper is routed without a writable harness (§17 The keeper), and whether memory is shared between people (no: VicBot serves one person, see the non-goals in the Thesis).
